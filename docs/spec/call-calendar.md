# Call Calendar — спецификация первой версии

Статус: утверждена владельцем проекта 23 сентября 2026 года в рамках [«Подготовить и утвердить итоговую спецификацию Call Calendar»](https://github.com/apriakhin/python-project-386/issues/31).

Этот документ описывает внешнее поведение сервиса и публичный API-контракт, по которым можно составлять тикеты на реализацию и впоследствии описать API в TypeSpec. [Макет Call Calendar](https://files.hexlet.app/a/2ipc5m) задаёт основные гостевые экраны; решения о поведении и контракте зафиксированы в [карте согласования](https://github.com/apriakhin/python-project-386/issues/22) и её дочерних билетах. Термины предметной области определены в [CONTEXT.md](../../CONTEXT.md).

## Область первой версии и доступ

- Есть один заранее заданный владелец календаря, один общий календарь и один фиксированный вид события — «Звонок». Справочника видов событий, редактируемого названия, описания, отдельного идентификатора вида и выбора вида гостем нет.
- Гость без регистрации и входа может открыть публичную главную страницу с описанием сервиса и переходом к бронированию, выбрать слот, забронировать событие и просмотреть публичную страницу «Предстоящие события».
- Владелец управляет расписанием через штатную Django admin с входом персонала. Отдельного React-интерфейса владельца и административных операций в публичном TypeSpec-контракте нет. Без входа и необходимых прав действуют стандартные ограничения Django admin.
- Отмена и перенос бронирования, ссылка на звонок и дополнительное описание события не предусмотрены.

## Время, расписание и слоты

- Единый фиксированный часовой пояс календаря — `Europe/Moscow`. Он не редактируется. Даты, интервалы расписания и окно бронирования определяются по московскому времени; в гостевом интерфейсе время сопровождается явной подписью пояса.
- Окно бронирования охватывает 14 календарных дат: сегодня по Москве и следующие 13 дней включительно. Начало слота должно быть строго позже текущего момента; дополнительного буфера нет.
- Длительность каждого слота и события — ровно 30 минут. Начала кандидатов идут с шагом 30 минут от начала каждого интервала расписания. Кандидат целиком помещается внутри **одного** интервала одного дня и не приходится на закрытую дату. Если местное начало не существует или неоднозначно из-за перехода часов, такой слот не предлагается; существующие события сохраняют свои моменты времени.
- Владелец задаёт одно регулярное недельное расписание. На каждый день недели допустимо несколько непересекающихся интервалов; отсутствие интервалов означает отсутствие предложений на этот день. В Django admin интервалы можно добавлять, менять и удалять. При сохранении отклоняются интервалы с концом не позже начала, переходящие через полночь и пересекающиеся с другими интервалами того же дня.
- Владелец может добавлять и удалять закрытые целиком будущие даты, включая даты за пределами текущего окна бронирования. Прошедшие закрытые даты не редактируются. Особых часов или разового открытия даты нет. Пустое расписание не предлагает слотов и не позволяет бронировать.
- Существующие бронирования не отменяются при изменении расписания или закрытии даты. Новые предложения строятся по обновлённым правилам.
- Брони одного календаря не пересекаются: конец одного события может совпасть с началом следующего. При конкурирующих запросах на пересекающиеся интервалы успешна только одна бронь; остальные получают отказ без создания события.

## Гостевой сценарий

1. На странице бронирования видны все 14 дат окна, включая даты без свободных слотов. Пустые даты неактивны; до выбора даты показана подсказка. Если свободных слотов нет во всём окне, показано состояние отсутствия доступности и продолжить нельзя.
2. Для выбранной даты показаны интервалы со статусами «Свободно» или «Занято» и число свободных слотов. Занятый интервал выбрать нельзя. Продолжить можно только после выбора свободного слота. Сводка выбора показывает дату и время с подписью московского пояса.
3. На следующем шаге гость видит сводку и обязательные поля «Имя» и «Email». Имя после удаления пробелов по краям не пустое и не длиннее 255 символов; email должен иметь корректный формат и быть не длиннее 254 символов. Ошибки полей показываются рядом с ними без потери введённых данных. «Изменить» возвращает к выбору слота без создания брони; при повторном переходе на форму имя и email сохраняются.
4. При успешной брони экран подтверждения показывает дату и время события и сообщение «Бронь подтверждена. До встречи!». «Забронировать еще» начинает новый поток: обновлённая доступность, пустой выбор и пустые поля гостя.
5. Если слот успели занять или он уже недоступен, событие не создаётся: гостю сообщается о недоступности, интервалы обновляются, затем гость возвращается к выбору с сохранёнными именем и email. При иной ошибке отправки гость остаётся на форме с введёнными данными и может повторить попытку; экран успеха не показывается.

## Предстоящие события

- Страница «Предстоящие события» доступна без входа. В список входят события, начало которых ещё не наступило, включая события за пределами текущего окна бронирования. Начавшийся звонок исключается.
- Ближайшее по началу событие идёт первым; список разбит на страницы по 20 событий. Карточка показывает имя и email гостя, дату и интервал звонка с подписью московского времени, дату и время создания брони. Публичный показ имени и email согласован владельцем проекта.
- Если событий нет, страница показывает текст «Предстоящих событий пока нет».
- В Django admin владелец видит всю историю событий, включая прошедшие, с именем и email гостя, интервалом и временем создания брони.

## Публичный API-контракт

Все три операции публичны и не требуют входа. Моменты времени в запросах и ответах представлены ISO 8601 с явным смещением `+03:00`; `date` — строка `YYYY-MM-DD` по московскому календарю. Публичный объект `Event` имеет поля:

| Поле | Значение |
| --- | --- |
| `id` | Устойчивый идентификатор события. |
| `name` | Имя гостя. |
| `email` | Email гостя. |
| `startAt` | Начало события, ISO 8601 с `+03:00`. |
| `endAt` | Конец события, ISO 8601 с `+03:00`. |
| `createdAt` | Время создания брони, ISO 8601 с `+03:00`. |

Поля вида события в `Event` нет: «Звонок» — единственный фиксированный вид.

### `GET /api/availability/`

Без параметров. Ответ `200`:

```json
{
  "timezone": "Europe/Moscow",
  "dates": [
    {
      "date": "2026-09-23",
      "slots": [
        {
          "startAt": "2026-09-23T10:00:00+03:00",
          "endAt": "2026-09-23T10:30:00+03:00",
          "status": "available"
        }
      ]
    }
  ]
}
```

`dates` всегда содержит все 14 дат, начиная с сегодняшней по Москве, по возрастанию. `slots` отсортированы по началу; возможные статусы — `available` и `busy`. Занятые кандидаты присутствуют со статусом `busy`; дата без кандидатов содержит `slots: []`. При отсутствии доступности возвращается обычный `200`, не отдельная ошибка. Пример показывает лишь один элемент массива; реальный ответ содержит все 14 дат.

### `POST /api/bookings/`

JSON-тело: `{ "startAt": "2026-09-23T10:00:00+03:00", "name": "Имя", "email": "guest@example.com" }`. Все поля обязательны. `startAt` — начало выбранного 30-минутного слота; временный идентификатор слота не используется. Перед созданием события сервер заново проверяет доступность и атомарно исключает пересечения.

- Успех: `201`, тело — объект `Event`.
- Некорректные или отсутствующие поля, включая синтаксически неверный `startAt`: `400` в едином формате ошибки; ошибки отдельных полей находятся в `fieldErrors`.
- Синтаксически корректный момент, который занят, устарел, уже прошёл либо не соответствует окну или расписанию: `409` с `code: "SLOT_UNAVAILABLE"`. Клиент заново запрашивает доступность и возвращает гостя к выбору.

### `GET /api/events/?page=N`

`page` — положительное целое, по умолчанию `1`; размер страницы всегда `20`. Ответ `200`:

```json
{
  "items": [],
  "page": 1,
  "pageSize": 20,
  "total": 0,
  "nextPage": null
}
```

`items` содержит публичные объекты `Event` с ещё не наступившим началом по возрастанию `startAt`, в том числе вне окна бронирования. `total` — число предстоящих событий на момент запроса, `nextPage` — номер следующей страницы или `null`. Пустой список и страница за концом дают `200` с `items: []` и `nextPage: null`. Некорректный `page` даёт `400` с `code: "INVALID_REQUEST"`.

### Ошибки

Единый формат тела ошибки для описанных случаев:

```json
{
  "code": "INVALID_REQUEST",
  "message": "Описание ошибки",
  "fieldErrors": { "email": ["Некорректный email"] }
}
```

`code` и `message` — строки; `fieldErrors` — необязательный словарь полей с массивами строк. Клиент ориентируется на HTTP-статус и `code`, а не разбирает текст `message`. Для неверного `page` определён код `INVALID_REQUEST`; для недоступного слота — `SLOT_UNAVAILABLE`. Прочие непредвиденные сбои не отображаются как успешная бронь: данные формы сохраняются для повтора.

## Границы документа
